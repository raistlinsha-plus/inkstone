# v0.7.5 本地检索对照

[合成语料和判定标准](retrieval-cases.json)在首次运行前固定。语料包含 9 份 Markdown、6 个手工整理的 Wiki 主题和 17 道题，使用与早期评测不同的资料和问题。题目的必要原文由文档标识与行号定义，覆盖精确查询、跨文档比较、同义改写、多事实组合、冲突、资料不足、范围限制及原文过期。这里的独立指语料与此前基准分开，语料、Wiki 和标注由同一次开发过程编写。

两组使用相同的查询清洗、生产 SQLite FTS5 BM25、范围与版本核对、候选排序和 6,000 字符证据上下文。对照组只执行 BM25，实验组加上生产 Wiki 检索与候选融合。Wiki 页通过实际存储和发布检查写入隔离临时库，Wiki 命中的引用回到当前原文核对。测试只创建临时文档，不使用本机 Inkstone 资料、钥匙串或模型服务。

## 判定方法

- 候选覆盖以排序后保留的候选为准。文档、原文行号和该行完整文本都匹配时，才计入该必要片段。
- 上下文覆盖以实际可送入生成阶段的片段为准。测试逐条核对这些片段的文档标识、当前文件哈希、行号范围和原文文本。该检查衡量原文定位准确性。
- 完整题要求所有已标注的必要片段进入上下文。冲突题要求两份相反来源都进入上下文。部分题的一部分答案可取证，另一部分没有材料。缺少证据的题记录是否仍有内容进入上下文。测试同时强制检查文档范围和原文过期约束。
- 检索耗时从清洗问题到构造上下文为止，不含导入和建索引。两组交替先跑，近邻秩法计算 p50 和 p95。单机、小样本、测试构建下的耗时只反映本次运行。

## 复跑

```sh
cargo test --manifest-path src-tauri/Cargo.toml --locked --lib independent_offline_retrieval_v075 -- --nocapture
```

如需逐题 JSON，在同一命令前设置 `INKSTONE_V075_RETRIEVAL_REPORT`，值为父目录已存在、目标文件尚未创建的绝对路径。报告包含语料 SHA-256、每题检索时间、命中的必要片段和可引用的原文范围。模型请求次数为零。生成回答的准确性、引用支持率、拒答表现与端到端耗时留空。

## 本次结果

| 指标 | BM25 | BM25 加 Wiki |
| --- | ---: | ---: |
| 必要原文进入候选 | 15/19 | 19/19 |
| 必要原文进入上下文 | 12/19 | 12/19 |
| 证据齐全的完整题 | 7/11 | 7/11 |
| 两份相反证据都进入上下文的冲突题 | 1/2 | 1/2 |
| 已知原文进入上下文的部分题 | 1/1 | 1/1 |
| 无支持题仍有上下文 | 0/3 | 0/3 |
| 文档标识、版本和行号全部匹配原文的上下文片段 | 13/13 | 13/13 |
| 检索 p50 / p95 | 1.738 / 2.857 ms | 5.996 / 9.975 ms |

Wiki 在三道改写题中补回四条候选原文。这四条均未通过证据选择。两组都遗漏了多事实题中的签收单去向，以及要求比较值班表与作业卡时的两条冲突证据。较短的巡检间隔问题保留了这两条冲突证据。三道无支持题包含一个有关键词候选但缺少所问属性的场景和一个旧原文失效场景，两组上下文均为空。

这次观察到的收益是候选覆盖，进入上下文的证据覆盖保持持平。向量、重排、在线检索、Wiki 生成和答案质量需要各自对照。生产检索阈值与策略未根据这套题调整。
