# Inkstone 从 RC.4 到 1.2 的开发计划

2026-11-22 评审稿。当前公开版本为 v1.0.0-rc.4。建议下一次迭代用 RC.5 改善资料问答，1.0 正式版按已有证据门槛放行。下一次功能发布用 1.1 把文档、问答和日历里的行动项连起来。本页包含 RC.5 的实施方案；任务格式、交互和写回协议单列在[1.1 技术设计](v1.1-tasks.zh-CN.md)。

## 一、各版交付给谁，怎样判断做完了

| 版本与优先级 | 用户能完成的事 | 主要交付 | 进入下一步的条件 |
| --- | --- | --- | --- |
| v1.0.0-rc.5 · P0 | 用自己的话连续问一篇笔记。问到两件事、笔记只写了一件时，仍能拿到有出处的那一项 | 逐项证据流失诊断、追问绑定、部分作答与可定位引文 | 在冻结回归中实质改善，公开分组成绩、代价和剩余错题。建议判定见第三节 |
| v1.0.0 · 正式源码版 | 在自己的 Mac 上完成导入、写作、提问、核对、整理 Wiki、备份及恢复 | 冻结一个候选提交，在相同制品上做独立人工盲评、原生验收和升级回退，统一手册、标签、源码包 | 通过既定 1.0 放行条件；若失败，发布下一轮有针对性的 RC。数据丢失、越权或严重事实错误阻断正式版 |
| v1.0.x · 按需维护 | 老用户可放心继续写作、更新或回退 | 优先处理资料一致性、崩溃、引用错配与输入法阻断；按受影响路径回移修复 | 每个补丁能用一个原始复现和一个反例验证。维护分支可与 1.1 原型并行 |
| v1.1.0-alpha.1 · 任务基础 | 在纪要中跟踪一个待办，从空间清单点回原段落 | 正文插入、普通勾选项升级、稳定身份、聚合清单、离线重建 | 正文和清单任一处勾选后结果一致，源码往返、复制导入、改名、重启不串项 |
| v1.1.0-alpha.2 · 日历联动 | 安排时间执行一项任务，并单独保留交付期限；给等待他人回复的事项定跟进日期 | 复用空间日历和现有日程；区分到期、执行时段、跟进 | 改执行时间不改截止日期；无日期任务可找回；原有日历块和 ICS 导出通过回归 |
| v1.1.0-beta.1 · 从聊天到行动 | 从一轮对话选出两条待办，改写一条、舍弃一条，保存到目标文档 | 选中一句直接创建、整轮按需提取、逐条确认、来源定位、重复提交保护 | 只有确认的条目落盘，模型不可用仍可手动创建；同一轮重试、换文档或删除会话均有明确结果 |
| v1.1.0 · 第一个完整任务版本 | 会后把行动项写回纪要，次日从日历继续处理，再回原文完成 | 收拢「任务与日历」入口，完成第一次使用、无障碍、长文与恢复验收 | 建议观察 5 人，至少 4 人在已有纪要和对话的前提下，1 分钟内把两项任务写入纪要并为一项排期。另测从日历回到原段和三处同步。记录耗时、误建和需要帮助的步骤 |

Alpha 和 Beta 是交互与数据格式的评审点，按成熟度选择是否公开，减少频繁打包。1.0.x 接收日常故障；1.1 的任务格式在通过复制、源码编辑和旧库恢复测试后再进入日常资料。

### 多语言与上下文使用说明怎样接入各版

| 时点 | 语言 | 对话与书房同伴 |
| --- | --- | --- |
| RC.5 | 盘点硬编码文案、中文日期、模型提示和检索假设，用一小段界面验证简中／英文切换 | 在已有的合成问答回放中记录每步用了什么、哪里丢了证据；据此修复追问。原生和人工盲评仍按 1.0 原定口径放行 |
| 1.1 Alpha 至 Beta | 同一应用使用语言资源；优先贯通设置、任务、聊天和日历的中英文路径，测试跨语言资料的出处定位 | 回答下提供「本轮上下文」，同伴回顾提供「为什么提起这件事」。聊天提取任务时显示实际用到的回合、原话与目标文档 |
| 1.2 | 建议把完整简中／英文界面、首用引导、错误提示和无障碍文案列为交付目标；繁中、日语、西语等逐个试点，按校对人手和质量验收标注支持程度 | 根据试用补轮间变化与用量说明；先验证用户能辨别“找到资料、发给服务、回答引用、同伴记住”的区别，再决定要不要加趋势图 |

1.1 的 4–6 周原估算针对任务主流程。若仍由一位开发者串行完成，建议为双语关键路径、上下文使用记录及两种语言的原生验收另留 1–2 周，Alpha 实测后再修订；全量翻译校对和额外语种另排。时间不足时先保证任务往返、授权范围和引用可靠，顺延趋势图和新语种。两项详细设计见[多语言交付](localization.zh-CN.md)与[对话和同伴的上下文](context-and-companion.zh-CN.md)。

## 二、为什么下一版先改问答

RC.4 的 40 个目标轮次共含 53 个可答要点。关键词模式离线回放时，前八个候选覆盖 50 个，准入候选覆盖 21 个，最终来源覆盖 15 个。10 个追问中，前八个候选覆盖 10/13 个要点，准入后为 0/13。在配对题的真实模型运行中，带正确近邻引文的要点也是 15/53；离线来源覆盖与在线作答分别计量。优先检查「找到原文以后，哪条规则把原句丢掉」；加大向量索引、换模型或扩大上下文的决策，留到同题对照有证据时再做。[离线分阶段数据](../../evals/v1.0/rc4/candidate-offline-summary.json) · [真实评测](../DELIVERY-v1.0.0-rc.4.md)

**示例。** 用户问「周六阅览室几点关，讲座几点开始？」原文只写了「周六阅览室 17:00 关闭」。理想回答给出「阅览室 17:00 关闭」及其可点击引文，然后明确「这篇记录中尚未核实讲座开始时间」。用户接着问「那周日呢？」若两个主体都可能被指代，只澄清影响答案的那一点。上轮模型的答复可以帮助理解问题，事实仍需从当前授权原文重新取得。

## 三、v1.0.0-rc.5 的技术与验证

### 改动顺序

| 步骤 | 复用与拟改之处 | 可检查的结果 |
| --- | --- | --- |
| 1. 建立逐项对照 | 扩展既有合成评测轨迹，给同一小问关联召回、准入、原句绑定、最终上下文和作答。记录首个丢失阶段与原因，例如对象不明、日期不匹配、预算截断或引文过期 | 从每个主要失败组挑一项，能沿记录定位到第一次丢证。单列召回本来就缺原文的题。常规用户日志仅保留必要计数，不记录私人原句。[评测轨迹](../../src-tauri/src/eval_trace.rs) |
| 2. 修复追问与部分缺证 | 在既有证据选择和运行时用本轮明确对象、问题关系、日期条件、限定文档来解析小问。上一轮已确定对象仅供消歧；新日期覆盖旧日期。每个小问分别绑定已核实原句，分别记录已支持、待核实、冲突或歧义。已支持项与其来源一起进入答案装配 | 同一文档中相近名称、异日记录、否定和单位都有反例。一个未答小问不会吞掉另一项已核实的时间。冲突并列给出处。[证据组装](../../src-tauri/src/candidate_reading.rs) · [原文绑定](../../src-tauri/src/evidence_reader/binding.rs) · [问答运行时](../../src-tauri/src/assistant_runtime.rs) |
| 3. 原句核对与呈现 | 优先本机核对；沿用设置中单独启用的辅助选句，每轮至多一次、8 段、合计 4,000 个原文字符。模型只提议当前候选中的句子，Rust 核对所属文档、版本、行、对象和条件。普通相关段落保留为阅读线索，界面明确标为待核实 | 设置关闭时不触发额外选句；远程失败仍可返回本机已证实项。生成前和返回前复核范围，切换文档、撤权或取消可丢弃过期结果。点击引用须能回到正确原文。[读证据接口](../../src-tauri/src/evidence_reader.rs) · [引用核对](../../src-tauri/src/answer_validation/citations.rs) |
| 4. 区分故障来自取证还是生成 | 固定同一模型、提示、预算和资料，比较 RC.4、候选、仅评测时直接提供标注原句三条路径。按开启/关闭辅助核对分开统计；再抽查 BM25、混合、混合加重排三个配置是否引入回退 | 公布整题、分项、追问、拒答、严重错误、HTTP 次数及 P50/P95。人工直供仍错则优先改生成或引用，准入已丢则修准入；仅在召回缺失组评估排序调整。[既有对照方法](../../evals/v1.0/rc3/README.md) · [配对评分](../../evals/v1.0/rc4/RUBRIC.md) |

**两条真实入口各测一次。** 编辑器右侧「问这篇文档」经 Rust 的资料问答命令；独立问答中主动添加文档或临时附件走其会话运行时。两者可共用逐项取证和引用校验，范围解析、附件失效和历史承接仍需各测。验收用同一个复合问题从两处进入，并各测一次改稿、追问和取消。通用翻译继续直接处理选中的文字。[资料问答命令](../../src-tauri/src/lib.rs) · [独立会话运行时](../../src-tauri/src/assistant_runtime.rs)

### 何时可以叫 RC.5，何时可以叫 1.0

下表的 RC.5 目标是**建议在动手前冻结的迭代目标**。配对题和 52 题都已用于比较，只作回归。单次模型波动需对两版在相同配置下重跑关键分组并保留两次结果。

| 指标 | RC.4 已知基线 | 建议 RC.5 的判定 |
| --- | --- | --- |
| 40 个目标轮次整题严格通过 | 15/40。20 对问题的双变体都通过为 5/20 对 | 目标 ≥24/40，且双变体都通过 ≥8/20 对。两个分母单独报告 |
| 前八个候选中已有直接原句的小问 | 离线前八覆盖 50/53；线上与离线完全可比的小问须另计 | 沿用 1.0 设计中的 ≥75% 正确且有据试行目标。只以检索问句、资料范围、提问历史均匹配且候选确有原句的小问为分母，报告样本数及未匹配数 |
| 部分缺证、追问、全缺证 | 部分缺证严格通过 2/13 题；追问正确且带引用 0/13 个要点；全缺证严格通过 7/7 题 | 目标依次为 ≥6/13 题、≥5/13 个要点、保持 7/7 题；核查每个新增正确答案的引用 |
| 来源、严重错误和旧回归 | 配对题中有严重错误的轮次 2/40；旧 40 题中的有据题取齐 22/34 | 严重错误与跨范围返回均为 0；按原计划恢复旧集 27/34，保住 9/9 和预计算向量集 49/52。独立 52 题对照 6/52 并公布退步项 |
| 成本与交互 | 现有配对试验含铺垫共 50 轮，25 次 HTTP，端到端 P95 3.79 秒；大量问题在本机提前结束 | 将本机提前结束和实际出答分别计时，公布每个正确且有据的要点消耗的请求数。请求或 P95 上升时用同一批问题说明新增正确项和等待代价，再决定默认路径 |

**正式版沿用原放行条件。** 由独立人员在开发前封存至少 40 道新题、标准答案和范围，冻结候选后由人盲评。关键问答正确率 ≥90%，关键断言引用支持率 ≥95%，严重错误 0。单列部分缺证、拒答、超时和服务失败。Wiki 初建、改稿、撤权、重开再问，通用翻译、禁网与自动联网，CLI 只读授权与撤销，原生编辑、备份恢复与升级回退，均以同一候选验收。公开源码与公证安装包沿用各自的发行条件。[完整放行清单](v1.0.zh-CN.md)

## 四、投入、评审和取舍

以一名熟悉仓库的开发者、可用的 Apple Silicon 验证机和独立评审人员为估算前提。以下是排期预算，真实模型、用户招募和公证等待另计。

- **RC.5 约 6–10 个工程日。** 前 1–2 日在合成资料上冻结口径、逐项定位；中间 3–5 日只修主要失败组并加反例；最后 2–3 日做同题对照、原生验收和交付评审。先从 10 个追问与旧集丢失的 5 道有据题开始。若回归仍红，先定位新引入的错项，保留当前公开候选。
- **1.0 放行预留 3–5 个工程日及独立用户测试窗口。** 开发 RC.5 时就准备未曝光题和招募体验者；最后锁定同一提交、模型配置和安装制品，集中跑一次完整验收。记录真实评分和分母，达标后再定发布日期。7 日回访可单列跟进。
- **1.1 预计 4–6 个工程周。** 任务格式与编辑往返约 1–2 周，日历联动约 1 周，聊天确认与去重约 1 周，余量给并发、恢复及小规模可用性测试。可在等待外部盲评时，用隔离空间验证任务格式。若 Markdown 往返无法保留任务身份，先解决再扩大试用。
- **1.1 之后按证据择一投入。** 若试用者频繁漏掉「等回复」或截止任务，1.1.x 优先做用户主动开启的本地提醒；若外部 AI 客户端使用现有 CLI 的配置持续卡住，评估只读 MCP 适配；若导入成为主要阻力，则优先带页码引用的文本 PDF。书房同伴可先试一个手动唤起的今日待办摘要，根据五个自然日的遮挡和打扰观察再决定动效。系统悬浮、多人派单和无人确认的外发另行立项。

每次冻结候选前只打一次验收包，开发期间按模块跑回归。当次文档写明“做了什么、在哪个构建验证、剩下什么”，API 等待和人工操作单独计时。公开 GitHub 时更新中英文入口和校验文件；更新日常应用、项目空间文档按各次交付的实际授权进行。
